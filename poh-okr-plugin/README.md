# poh-okr-plugin

Раздел «Управление целями» для DeepSeek Harness: доска OKR на квартал, планирование
по спринтам и операционные задачи PO.

Плагин — **необязательная часть** `poh-okr-agent`. Репозиторий остаётся самодостаточным
набором навыков для Claude Code: `install.sh` синкает `skills/` (и `commands/` тем агентам,
которые каталога навыков не читают), эта папка в установку не попадает и Node.js для
навыков `/okr-*` не нужен.

## Хранилище

Своего хранилища у плагина нет. Всё живёт в [Backlog.md](https://github.com/MrLesk/Backlog.md)
и читается через его CLI:

| Сущность | Backlog.md |
|---|---|
| Объектив (OBJ) | milestone |
| Ключевой результат (KR) | задача типа `okr` с привязкой к milestone |
| Фаза KR в спринте | метка `okr-phase:s<N>:<фаза>` на задаче KR |
| Операционная задача PO | задача типа `potask`, связь с KR — `--dep` |
| Вкладка панели работы | метка `okr-kind:task` / `okr-kind:control` / `okr-kind:risk` |
| Срок | `--due-date` задачи или объектива |
| Ссылка на Confluence | `--doc` |
| Ссылка на эпик трекера | `--ref` |
| Событие ленты KR | комментарий задачи (`--comment`) |

Связь операционной задачи с KR — зависимость, а не родительство: подзадача получила бы
идентификатор вида `PO-20.1` и стала бы частью KR, тогда как у неё свой жизненный цикл.

### Задачи, договорённости и риски

Все три вкладки панели работы — это **один тип задач Backlog.md, `potask`**. Отдельных
типов под договорённость и риск нет намеренно: тип в Backlog.md влияет на фильтры и отчёты
CLI, а здесь речь о трёх видах одной сущности с общим жизненным циклом. Вид задаётся
меткой, и сменить его — это правка одной метки, а не пересоздание задачи.

| Вкладка | Метка вида | Что это |
|---|---|---|
| Задачи | `okr-kind:task` | работа PO: сделать, написать, согласовать |
| Договорённости | `okr-kind:control` | что кто-то пообещал — контроль исполнения |
| Риски | `okr-kind:risk` | что может помешать цели |

Каждая задача любого вида несёт на себе:

| Поле | Где в Backlog.md |
|---|---|
| Название | заголовок задачи |
| Описание с блоками | markdown в описании задачи (`--description`) |
| Срок | `--due-date`, формат `YYYY-MM-DD` |
| Приоритет | `--priority high\|medium\|low`; невыставленный так и остаётся пустым |
| Выполнено | статус `Done` |
| Привязка к KR | метка `okr-kr:<id KR>` **и** зависимость `--dep <id KR>` |

Привязка к ключевому результату записывается дважды нарочно: зависимость — это сама связь,
а метка её дублирует, потому что `task list --json` зависимостей не отдаёт, и без метки
панели пришлось бы открывать каждую задачу по отдельности ради одной стрелки.

Как это выглядит в CLI. Создание — ровно то же, что делает кнопка «+» в панели:

```sh
# договорённость со сроком, привязанная к KR PO-42
backlog task create "Ромашкин пришлёт список эпиков" \
  --type potask --labels okr-kind:control,okr-kr:PO-42 --dep PO-42 \
  --due-date 2026-09-15 --priority high
```

Просмотр того, что панель показывает во вкладке:

```sh
backlog task list --type potask --plain          # все три вкладки сразу
backlog task list --type potask --json | jq '.tasks[] | select(.labels[]? == "okr-kind:risk")'
```

Смена вида — снять старую метку и поставить новую; плагин делает это одной командой из
подвала карточки задачи:

```sh
backlog task edit PO-51 --remove-label okr-kind:task --add-label okr-kind:risk
```

**Секции панели считаются, а не хранятся.** «Просрочено / Сегодня / На неделе / Позже / Без
срока» выводятся из `--due-date` в момент отрисовки: метка про срок разъезжается с самим
сроком в тот же день, когда срок наступает, и хранить обе — значит выбирать, какая из них
врёт. Секция «Выполнено» показывает только закрытое **за последние сутки**: отметки «когда
выполнено» у Backlog.md нет, поэтому свежесть считается по времени последней правки задачи
(`updatedAt`). Более старое выполненное из панели уходит, но никуда не девается:

```sh
backlog task list --type potask -s Done --plain
```

Фактические фазы на доске и плановые спринты по стадиям — независимые поля. Плановый
спринт влияет только на граф детальной страницы, фактическая фаза — только на доску.

Писать в `.md` напрямую плагин не умеет и не должен: единственный писатель — CLI, он держит
метаданные задач в согласованном состоянии.

## Требования

**Backlog.md 1.51.0 или новее.** Дедлайны задач и объективов появились именно в нём, а на них
держится группировка панели работы. На версии старше плагин отказывается работать с внятным
сообщением вместо тихой потери функциональности.

```sh
npm i -g backlog.md@latest
```

Типы задач `okr` и `potask` должны быть заведены в воркспейсе. `backlog config set` их не
принимает — CLI отправляет править файл проекта:

```yaml
# backlog/config.yml
types: ["bug", "feature", "enhancement", "task", "chore", "docs", "spike", "okr", "potask"]
```

## Подключение к DeepSeek Harness

1. Собрать пакет:

   ```sh
   cd poh-okr-plugin && pnpm install && pnpm build
   ```

2. Слинковать в каталог плагинов харнесса:

   ```sh
   ln -s "$PWD" <harness>/harness-ui-plugins/poh-okr-plugin
   ```

3. Добавить запись в профиль `web`. `cordis.patch.yml` едет вместе с пакетом и задаёт
   всё, кроме корня воркспейса, — его укажите слоем профиля по идентификатору `okr-goals`:

   ```yaml
   - id: okr-goals
     config:
       workspaceRoot: '/путь/к/воркспейсу'
   ```

4. Открыть навыки `/okr-*` харнессу. Кнопки раздела («Планирование OKR», «Сгенерировать
   презентацию») отправляют в чат `/okr-draft` и `/okr-equator` — первый сам добирает
   `/okr-index` и `/okr-context`, если контекста квартала ещё нет, так что нажатие
   проводит пайплайн с нужного места. Харнесс ищет обе команды среди навыков, а не
   команд Claude Code, — без корня ниже они отвечают «нет в каталоге»:

   ```yaml
   - id: skill-filesystem
     name: '@deepseek-ai/dsh-skill-filesystem'
     disabled: false
     config:
       customSkillDirs:
         - '/путь/к/poh-okr-agent/skills'
   - id: tool-skill
     name: '@deepseek-ai/dsh-tool-skill'
     disabled: false
   ```

   Обе записи обязательны: в профиле `web` они выключены по умолчанию, и без `tool-skill`
   каталог навыков задан, но инструмента `skill` у модели нет. Все корни перечисляются
   **одной** записью `skill-filesystem`: вторая запись с тем же идентификатором заменяет
   список первой, и ранее подключённые навыки молча пропадают из каталога.

5. Перезапустить харнесс и дождаться ответа `200`.

**Плагин без собранного `lib/index.js` роняет харнесс целиком** — cordis считает такую запись
фатальной. Каталог `lib/` не в репозитории, поэтому после свежего клона сборка обязательна.

|---|---|---|

## Что уже работает

Панель работы (три вкладки, секции по срокам, отметка выполнения, карточка задачи с меню
блоков), доска целей (объективы, ключевые результаты, фазы по клику), сайдбар KR (описание,
ссылки, планирование по стадиям) и детальная страница (граф связей, лента событий с
чипами-фильтрами).

Отличия от прототипа, сделанные осознанно:

- **Хром раздела — на токенах темы харнесса**, а не на «бумажной» палитре прототипа: светлый
  лист внутри тёмной оболочки читается как сломанный экран. Палитра пяти фаз перенесена из
  спецификации дословно — она несёт смысл и должна быть одинаковой у всех.
- **Контекст задачи — markdown, а не HTML.** Хранилище общее с человеком и навыками: HTML
  в описании задачи нечитаем в `backlog task view`, в веб-интерфейсе Backlog.md и в самом
  `.md`-файле.
- **Меню блоков без пунктов «Attachment», «Subtask», «Tag» и «Linked task/note»**: у них нет
  соответствия в описании задачи. Подзадачи и связи в Backlog.md есть отдельными механизмами —
  им место в отдельной работе, а не в виде вставки текста.
- **«Что сделано» и «что осталось» в сайдбаре — списки связанных задач**, а не свободные
  текстовые поля: иначе они разошлись бы с панелью работы, показывающей те же задачи.
- **Событие ленты открывается только на чтение**: комментарий Backlog.md после записи его CLI
  не редактирует и не удаляет, а кнопки, которые ничего не сделают, хуже отсутствующих.

Ещё не сделано: иконка базы знаний (целевая страница не определена) и перетаскивание KR между
объективами.

## Разработка

```sh
pnpm test                                        # разбор и построение команд, без CLI
OKR_WORKSPACE_ROOT=/путь pnpm test               # плюс живой прогон против настоящего backlog
```

Без `OKR_WORKSPACE_ROOT` живые тесты пропускаются и **печатают об этом баннер**: зелёный итог
без живого прогона означает, что разбор реального вывода CLI никто не проверял.
