## Задача

В `poh-okr-agent` нужен механизм саморефлексии: регулярный (день или неделя)
диалог с PO в формате дейлика, который держит руку на пульсе целей квартала.

Суть ритуала - **регулярный диалог для актуализации контекста**. Агент через
этот диалог синхронизирует ожидания, чтобы был ежедневный каденс без разрыва
ожиданий. Всё остальное в дизайне подчинено этому.

### HowToDemo из постановки

1. PO открывает рабочее место.
2. В чате от okr-agent пришло сообщение с вопросами для саморефлексии над
   целями: что было сделано вчера, что команда делает сегодня, какие
   блокаторы решаются. Вопросы подготовлены заранее; агент уточняет, если
   было что-то важное, и помогает вспомнить.
   Цель диалога - убедиться, что целевые даты и задачи не потеряны,
   договорённости соблюдаются, эскалация или проработка целевых задач
   происходит своевременно.
3. PO отвечает на эти сообщения.
4. okr-agent фиксирует знания в своей памяти.
5. okr-agent на основе рефлексии предлагает целевые действия на сегодня.
6. okr-agent на основе рефлексии напоминает точки контроля: от кого, что
   ожидаем, почему, в какие сроки.
7. PO использует полученные знания для работы.

### Пожелания из постановки

- Операционный беклог вести через `.md`-заметки Backlog.md
  (https://github.com/MrLesk/Backlog.md) в `.okr/backlog`, задачи с
  префиксом `OKR`.
- После каждой синхронизации знания фиксируются в git-истории, чтобы
  исторически восстановить контекст.

## Принятые решения

### Р1. Интеграция с `poh-backlog-skills`: вариант A

`poh-okr-agent` выступает host-агентом, `poh-backlog-skills` подключается
опциональным модулем.

Ритуал и диалог живут в `poh-okr-agent`. Он читает `.okr/backlog`, собирает
`items.json`, зовёт `poh-backlog run`, получает находки и план и вплетает их
в вопросы дейлика. Пакета нет - ритуал работает, просто без правил гигиены.

Отклонённые варианты:

| Вариант | Почему нет |
|---|---|
| B: ритуал внутрь `poh-backlog-skills` | Его VISION буквально: «гигиена беклога как правила, а не как ритуал». Он не знает про цели квартала; тащить туда KR, точки контроля и даты - менять миссию репозитория |
| C: третий репозиторий `poh-daily-agent` | Без OKR ритуал вырождается в статус-митинг. Цена - третий слой памяти и третий выключатель |

Подтверждено PO: «backlog-management-agent» из постановки - это
`poh-backlog-skills`.

### Р2. Два среза

- **Срез 1 (этот документ):** ритуал с чистым швом транспорта. Работает в
  чате Claude Code с первого дня.
- **Срез 2 (отдельная спека):** транспорт и будильник - доставка вопросов в
  Telegram или MTS.Link, приём ответов, автономный запуск на машине.

Причина разведения: транспорт содержит неизвестные (доступность API
MTS.Link, корпоративная политика на боты, приём ответов обратно), а ритуал
от них не зависит.

## Проверенные факты

Проверялось на живых инструментах, не по памяти.

### Backlog.md CLI (v1.48.0, установлен локально)

Обе хотелки из постановки поддержаны нативно:

```bash
backlog init "<project>" --backlog-dir .okr/backlog --task-prefix OKR --defaults
```

- `--backlog-dir <path>` принимает произвольный project-relative путь;
- `--task-prefix <prefix>` - только буквы, даёт id вида `OKR-1`, `OKR-2`;
- `--defaults` даёт неинтерактивный init;
- флаги `--agent-instructions none` и `--integration-mode none` вместе
  несовместимы: CLI отказывается, нужно указывать что-то одно.

Итоговый `backlog.config.yml` содержит `backlog_directory: ".okr/backlog"` и
`task_prefix: "OKR"`. Файл задачи - markdown с YAML-фронтматтером
(`id`, `title`, `status`, `labels`, `created_date`) и блоком Acceptance
Criteria в чекбоксах между маркерами `<!-- AC:BEGIN -->` и `<!-- AC:END -->`.

Два подводных камня:

- `auto_commit: false` по умолчанию - **Backlog.md сам ничего не коммитит**,
  фиксация в git остаётся на ритуале;
- `remote_operations: true` по умолчанию - предупреждает, если у репозитория
  нет remote. Онбординг должен либо потребовать remote, либо выставить
  `backlog config set remoteOperations false`.

### Шов в `poh-backlog-skills`

Пакет уже умеет Backlog.md. В `poh_backlog/memory.py`:

- `backlog_create_argv(run_id, state_dir)` - строит argv на создание задачи
  «Гигиена беклога, прогон {run_id}» с меткой `hygiene`, статусом
  `In Progress` и семью AC по стадиям: `audit`, `diff`, `plan`, `approve`,
  `apply`, `verify`, `snapshot`;
- `backlog_check_ac_argv(task_id, stage)` - отмечает стадию по индексу.

Обе функции **только строят argv и внутри пакета не вызываются нигде** - шов
оставлен снаружи для host-агента намеренно. Это и есть точка стыковки.

Прочее из контракта пакета, важное для интеграции:

- вход - нормализованный `items.json` (`BacklogItem`: `id`, `type`, `title`,
  `description`, `status`, `created_at`, `updated_at`, `labels`, `parent`,
  `estimate`, `extra`);
- выход - `findings.json`, `report.md`, `plan.md`, `plan.json`, снимок в
  `state/<run-id>/`;
- CLI: `poh-backlog run --items --out --state --run-id [--shadow]` и
  `poh-backlog approve --out --decisions`;
- три состояния галочки в `plan.md`: `[x]` утверждено, `[-]` отклонено
  навсегда в `decisions.yaml`, `[ ]` решения не было и действие вернётся;
- `run` отказывается перезаписывать `plan.md`, в котором уже есть отметки
  (код выхода 2);
- ноль сетевых вызовов, ничего деструктивного;
- маппинга Backlog.md среди источников нет - есть только
  `poh_backlog/data/mappings/github.yaml`. Нужен новый `backlog-md.yaml`,
  и он уходит PR-ом в `poh-backlog-skills`, а не форком.

## Секция 1: форма, границы, раскладка

**Статус: предложена, PO ещё не подтвердил.**

### Форма

Одна команда `/okr-sync [<quarter>]` плюс навык `skills/okr-sync/SKILL.md`.
Нового runtime нет: агент сам читает и пишет markdown, `backlog` вызывается
как внешний CLI, `poh-backlog` - опционально.

Деградация:

| Чего нет | Поведение |
|---|---|
| `backlog` CLI | Команда останавливается с инструкцией по установке |
| `poh-backlog` | Ритуал идёт без правил гигиены и сообщает об этом одной строкой |

### Раскладка

```
.okr/backlog/tasks/OKR-N - <название>.md   операционные задачи (Backlog.md)
.okr/sync/<YYYY-MM-DD>.md                  запись одной синхронизации
.okr/sync/pulse.md                         ожидания, точки контроля, договорённости
.okr/sync/state/                           снимки прогонов poh-backlog
```

`pulse.md` - единственный файл, который следующий прогон читает целиком.
Дневные записи - история; они не перечитываются пачкой, иначе контекст
растёт без границы.

### Границы

Ритуал не назначает задачи, не двигает статусы без ответа PO и не трогает
`OKR-<quarter>.md`: цели квартала правятся только через `/okr-draft`.

Он не заменяет `/okr-equator`. Экватор - отчёт наверх раз в квартал, дейлик -
удержание контекста внутри недели. Расхождения, найденные дейликом,
накапливаются в `pulse.md` и попадают в экватор как факты, а не переписывают
OKR на ходу.

### Что уже известно про срез 2

- **Telegram, отправка** - бессерверно: один HTTPS POST в Bot API. Токен и
  `chat_id` заводит PO, агент их не касается.
- **Telegram, приём ответов** - без сервера только опросом `getUpdates` из
  локального задания. Webhook требует публичный HTTPS-эндпойнт.
- **Автономный запуск на macOS** - `launchd`-агент, plist в
  `~/Library/LaunchAgents/`, работает при закрытом Claude Code, дёргает
  `claude -p` в headless-режиме. Онбординг ставит и снимает.
