# poh-okr-agent — дизайн

Дата: 2026-08-20. Автор: Claude (по запросу PO Ишманов Алексей).

## Миссия

Единственная цель репозитория — управление OKR-целями Product Owner: формирование
OKR, roadmap и верхнеуровневой декомпозиции с требованиями по ним, сборка
квартальной презентации плана для команды, и — флагманский навык — отчёт
«экватор квартала» (`.md` + `.pptx`) о статусе исполнения на середине квартала.

Переносимый навык по образцу `poh-bft-writer` и `poh-strategy-agents`:
подключается в любой воркспейс через `install.sh`, строит собственный контекст,
работает без внешних runtime-зависимостей (JIRA/Confluence MCP — опционально,
для живого статуса; без них навык работает на локальных доках с ручным вводом PO).

## Место в манифесте po-helper-org

**Функции: 1 · 4** (`.github/profile/README.md`, таблица «Контур PO»):
- 1 — снятие неопределённости: формирование OKR/roadmap, взятое из
  `poh-strategy-agents` целиком.
- 4 — риски и раннее предупреждение: отчёт-экватор — сигнал об отклонениях с
  последствиями для целей, до того как это станет эскалацией перед руководством
  (дословно из манифеста).

## Архитектура: pipeline из 9 команд

STOP-пауза после каждой — PO подтверждает переход, как в `bft-writer`/
`strategy-agents`. Каждая команда — отдельная роль и отдельный артефакт.

| # | Команда | Роль | Артефакт |
|---|---|---|---|
| 0 | `/okr-index` | Context Builder | `.okr/index/` (домен, глоссарий, стейкхолдеры, реестр источников, `MANIFEST.md`) |
| 1 | `/okr-context <quarter>` | Context Builder | `.okr/<quarter>/artefacts/okr-context-pack.md` |
| 2 | `/okr-draft <quarter>` | Objective/KR Designer | `.okr/<quarter>/OKR-<quarter>.md` |
| 3 | `/okr-debate <quarter>` | Devil's Advocate | вердикт в `OKR-<quarter>.md` |
| 4 | `/okr-roadmap <quarter>` | Roadmap Architect | `.okr/<quarter>/roadmap.md` |
| 5 | `/okr-decompose <quarter>` | Decomposer | `.okr/<quarter>/KR-EPIC-MAP.md` |
| 6 | `/okr-plan-deck <quarter>` | Deck Builder | `.okr/<quarter>/plan-deck.pptx` |
| 7 | `/okr-equator <quarter>` | Equator Reporter | `.okr/<quarter>/equator/экватор-<quarter>.md` + `.pptx` |
| 8 | `/okr-validate <quarter> <artefact>` | Validator | отчёт линтера в консоль/`artefacts/validation.md` |

### Роли по стадиям

**0. `/okr-index`** — как `/bft-index`/`/strat-index`: сканирует воркспейс
(локальные доки, код через serena MCP, трекер через JIRA/Confluence MCP —
опционально) и строит `.okr/index/`: `domain.md`, `glossary.md`,
`stakeholders.md`, `sources.md`, `MANIFEST.md` (покрытие INDEXED/UNAVAILABLE).
Запускается один раз при онбординге, перестраивается по запросу.

**1. `/okr-context <quarter>`** — собирает контекст-пак для формирования OKR:
цели бизнеса из индекса, предыдущий квартальный OKR (если есть, из
`.okr/<prev-quarter>/OKR-<prev-quarter>.md`), открытые вопросы прошлого
экватора. Факт vs вывод LLM размечается явно (`(источник)` / `[вывод LLM]`).

**2. `/okr-draft <quarter>`** — Objective/KR Designer формирует черновик
`OKR-<quarter>.md`: 3-5 Objectives, у каждого 3-6 Key Results с PBV
(Priority Business Value, шкала 1-9 — методология по умолчанию, переопределяется
в `okr-config.md`, если команда уже использует другую шкалу приоритезации).
Формат KR — измеримый и проверяемый (не активность, а результат).

**3. `/okr-debate <quarter>`** — Adversarial-проверка отдельным запуском (не
загрязняет составление): каждый KR проверяется на измеримость, реалистичность
(sandbagging vs недостижимость), пересечение с другими KR, скрытые
зависимости. Вердикт дописывается в `OKR-<quarter>.md`. Забраковано → назад на
`/okr-draft`.

**4. `/okr-roadmap <quarter>`** — Roadmap Architect строит `roadmap.md`:
now-next-later по каждому Objective, с привязкой каждого пункта к KR.

**5. `/okr-decompose <quarter>`** — верхнеуровневая декомпозиция и требования
по каждому KR: что входит/не входит в объём, как поймём что сделано (How to
Demo), верхнеуровневые эпики-кандидаты. **Не** полный БФТ — это explicit
границы, не корпоративный формат с БТ/ПТ/ИТ/ФТ/НФТ. На полный БФТ по эпику —
явная отсылка к `poh-bft-writer` (`/bft-context-gen` берёт `KR-EPIC-MAP.md` как
один из источников контекста, если репозиторий подключён рядом).

**6. `/okr-plan-deck <quarter>`** — собирает `.pptx` для кикофф-презентации
команде: цели квартала, roadmap, план по спринтам. Брендбук общий с
экватором (см. ниже), но структура слайдов не зафиксирована вложением —
разумный дефолт (титул → цели → roadmap → план по спринтам → риски входа),
донастраивается `okr-config.md`.

**7. `/okr-equator <quarter>`** — флагманский навык, детали в разделах ниже.
Одна команда — два артефакта (`.md` как источник правды, `.pptx` — производная
презентация из тех же данных).

**8. `/okr-validate`** — структурный лоу-level lint (как `bft-lint.py`):
обязательные секции присутствуют, PBV в диапазоне, статус — из
допустимого enum, в таблицах нет пустых обязательных колонок кроме явно
помеченных `[УТОЧНИТЬ]`. Тот же чек встроен автоматически в `/okr-draft` и
`/okr-equator` перед записью файла (как у `bft-writer`); `/okr-validate` —
для ручного повторного прогона/аудита.

## Экватор квартала — `.md`

Структура фиксирована шаблоном-ресурсом
`skills/okr-equator/resources/equator-report-template.md`, проверяется
линтером `okr-lint.py`. Обязательные секции (одна к одной с референсом):

1. Шапка: инициатива/команда, PO, период части 1 и части 2, дата составления,
   источники, легенда статусов, определение PBV.
2. **Главное за 60 секунд** — что сделано / планы на вторую половину /
   сложности (в 3 абзаца).
3. **Часть 1** (статус за первую половину квартала):
   - Сводка по цифрам (таблица: Инициатива × Всего/Выполнено/В
     работе/На паузе/В ожидании/Отменено).
   - На каждый Objective: Завершено · В работе/в ожидании · Актуальные риски ·
     Отменено — таблицы с колонками KR/Задача/PBV/Статус/Стадия/Что
     сделано/Что осталось.
4. **Часть 2** (план до конца квартала):
   - Сводка по цифрам (Активных KR / С коммитментом / Под вопросом).
   - На каждый Objective: таблица Коммитмент до конца квартала (KR/Задача/
     PBV/Коммитмент/Условие-риск).
   - Новые KR сверх исходного плана — отдельным блоком, с пометкой что PBV/
     статус не проходили формальную приёмку.
5. **Системные риски квартала** — не привязанные к одному KR.
6. **Открытые вопросы** — сводный список всех `[УТОЧНИТЬ у PO]` по документу.

Данные `/okr-equator` берёт из: `.okr/<quarter>/OKR-<quarter>.md`,
`roadmap.md`, `KR-EPIC-MAP.md`, опционально live-статус через JIRA MCP
(`jira_search` по project/epic-link), плюс прямой ввод PO по статусам,
которые не выводятся автоматически. Ничего не придумывается — расхождение
или неизвестность помечается явно, как во всех навыках po-helper-org.

## Экватор квартала — `.pptx`

Брендбук извлечён из вложенного `.pptx` (реальные `srgbClr`, не тема
по умолчанию):

| Роль | Hex | Применение |
|---|---|---|
| Доминирующий тёмный | `0F0F14` | фон титульных/разделительных слайдов, основной текст |
| Тёплый беж | `E4E0DA` | фон контентных слайдов |
| Белый | `FFFFFF` | текст на тёмном, карточки |
| Серый вторичный | `8A8A8A` | подписи, второстепенный текст |
| Тёмно-серый | `42424A` | текст на бежевом |
| Голубой (чип) | `A9DCEE` / `C9DDF5` | статус «в работе» |
| Мятный (чип) | `C7F8E2` / `CDE8D2` | статус «выполнено» |
| Розовый (чип) | `FFD9E2` | статус «отменено» |
| Персиковый (чип) | `F7DCC4` | статус «в ожидании» |
| Жёлтый (чип) | `FFEDB0` | статус «на паузе» / внимание |
| Акцент | `4C6FFF` | точечный, редкое использование |

Шрифты: **Arial** (заголовки, текст), **Courier New** (цифры/данные —
моноширинный технический акцент). Canvas: 20″ × 11.25″ (нестандартный
масштаб 16:9, не стандартные 13.33″×7.5″ — задаётся явно в `pptxgenjs`
через `pres.defineLayout` + `pres.layout`).

Структура — жёстко 27 слайдов, реализована кодом-генератором
(`skills/okr-equator/scripts/build_equator_pptx.js` на `pptxgenjs`), LLM
только передаёт данные, не решает раскладку:

1. Титул (период, PO, команды).
2. Сводка funnel (Выполнено/В работе/Не начато/Отменено × по Objective + итого).
3. Риски и проблемы (категории: Внешнее/Ресурс/Общее).
4. Roadmap на вторую часть (сетка по Objective).
5. Инициативы по спринтам (Gantt-подобная таблица, спринты × стадии).
6. Раздел-разделитель «Часть 2 · Полный отчёт».
7. Статус по инициативам (сводная таблица части 1).
8–12. Per-Objective квартет ×1: обзор-воронка по стадиям / часть2-план
   (в работе/в ожидании/новое) / часть1-детали (таблица) / новые задачи /
   риски и эскалации.
13–18, 19–23, 24–26. То же для остальных Objective (число слайдов на Objective
   плавает — «новые задачи» и «риски» пропускаются, если пусто, как в
   референсе на OBJ 4).
27. «Что нужно от руководителей» (карточки: тема / почему / конкретный ask).

## `plan-deck.pptx`

Тот же брендбук (палитра/шрифты/canvas), другой генератор-скрипт с более
гибкой структурой (разумный дефолт, не из вложения): титул → цели квартала
(Objectives) → roadmap → план по спринтам → риски входа в квартал.
Настраивается в `okr-config.md`, если у команды свой набор слайдов.

## `okr-config.md` (шаблон в корне репозитория)

По образцу `bft-config.template.md` / `domain-profile.template.md`:
имя команды/инициативы, текущий квартал, tracker project keys (для
`/okr-index` и живого статуса в `/okr-equator`), Confluence space
(опционально), шкала приоритезации (по умолчанию PBV 1-9), override
брендбука (если у команды свои цвета/шрифты), список стейкхолдеров
(«ГД», кому адресован экватор).

## Данные и границы

- **Нет фабрикации фактов.** Статус KR, риски, коммитменты — только из
  `.okr/<quarter>/` артефактов, трекера (если подключён) или прямого ввода PO.
  Неизвестное — `[УТОЧНИТЬ у PO]`, никогда не додумывается.
- **PBV по умолчанию 1-9**, переопределяемо в `okr-config.md`.
- **Полный БФТ — не сюда.** `/okr-decompose` даёт верхнеуровневые
  требования и границы; детальный корпоративный БФТ — задача `poh-bft-writer`
  (подключается рядом, читает `KR-EPIC-MAP.md` как контекст).
- **Портируемость.** Ноль обязательных внешних runtime-зависимостей;
  JIRA/Confluence MCP — опциональное обогащение, не жёсткая зависимость.

## Тестирование

- `okr-lint.py` — юнит-тесты на фикстурах (валидный/невалидный
  `экватор-<quarter>.md`), по образцу `test-bft-lint.sh`.
- `build_equator_pptx.js` — валидация через `scripts/office/validate.py`
  (из скилла `pptx`) на каждом изменении шаблона; визуальный QA через
  рендер в изображения перед первым релизом шаблона.
- Ручной прогон полного pipeline на синтетическом квартале (2-3 Objective,
  вымышленные KR) как smoke-test перед первым реальным использованием.
