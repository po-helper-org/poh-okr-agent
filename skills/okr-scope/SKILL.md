# Навык: OKR Scope

## Использование

```
/okr-scope <quarter>
```

Этап 2 из четырёх: `/okr-retro → /okr-scope → /okr-stages → /okr-teamplanner`.

## На выходе

```
.okr/<quarter>/plan/scope-<quarter>.json   источник истины
.okr/<quarter>/plan/scope-<quarter>.html   документ, вокруг которого идут правки
```

Формат данных и проверки — `resources/plan_schema.md`, эталон —
`scripts/fixtures/scope-2026Q4.json`. Скрипт — `scripts/okr-plan.py`.

## Принцип

Планирование начинается с разговора с PO, а не с анкеты. Сначала слушаешь
целиком, потом собираешь драфт, потом правите его вместе. Вопросы — только по
тому, без чего драфт не собрать, и по одному. Остальное — `[УТОЧНИТЬ у <кого>]`
в тексте драфта: PO увидит подсветку и поправит сам.

## Инструкция для LLM

### Этап 0: Вводные

1. `.okr/<quarter>/plan/retro-<prev>.json`:
   - принят → бери из него все KR с `carry` = Продолжение или Доделка;
   - черновик → скажи PO, что ретро не принято, и предложи сначала закончить
     `/okr-retro <quarter>`. PO хочет идти дальше — идём, ссылку на ретро
     всё равно ставим;
   - нет вовсе → спроси, есть ли прошлый квартал. Нет (первое планирование) →
     `retro_skipped` с причиной. Есть → предложи `/okr-retro <quarter>`.
2. `okr-config.md` → `team`, `po_name`, `role_tags`, `teams`.
3. `.okr/index/` (если есть) → команды, системы, стейкхолдеры, глоссарий.
   Нужен только как словарь: правильно назвать команды и системы из рассказа PO.
4. Уже есть `scope-<quarter>.json` → не начинай заново, переходи к Этапу 3.

### Этап 1: Выслушать PO

Отправь ровно это и жди ответа:

> Расскажи мне, что и для каких команд ты хочешь увидеть в <quarter>, в
> открытом виде — как рассказал бы коллеге. Можно голосом. Я из этого соберу
> первичный драфт.
>
> Из прошлого квартала переходит: <список Продолжений и Доделок из ретро или
> «ничего»>.

Не перебивай уточнениями. Ответ PO — поток речи: повторы, оговорки, «а, и ещё».
Сохрани его как есть в `po_brief`.

### Этап 2: Первичный драфт

Разбери рассказ:

1. **Команды** → `teams`. Смежные команды, от которых что-то нужно, —
   `external: true`.
2. **Цели** → `objectives`. Группируй инициативы по смыслу, а не по командам.
   Название цели — результат, а не работа: «Продавать подписку без ручных
   операций», а не «Сделать биллинг». `why` — какая боль и что станет лучше.
   Поддержку и регулярные работы — отдельной целью с `activity: true`.
3. **Инициативы** → `initiatives`. Для каждой: `title`, `teams`, `pbv`, `tag`,
   `result`. Для технических переключений — `before`/`after`.
   - `result` — что можно показать в конце квартала, а не «улучшить» и «обеспечить».
   - PBV: 9 — коммитмент с датой перед кем-то, 7–8 — без этого квартал не закрыт,
     5–6 — важно, 3–4 — если хватит сил, 1–2 — гипотеза. Выводи из слов PO
     («маркетинг ждёт к декабрю» → 9); нет сигнала → ставь 5 и помечай
     `[УТОЧНИТЬ PBV]` в `open`.
   - Не знаешь, как делать → `tag: RESEARCH`, результат — согласованный план.
4. **Переходящее из ретро.** Каждое Продолжение и Доделка — инициатива с
   `from_retro`. PO о нём не упомянул → всё равно добавь и спроси: «<id> из
   прошлого квартала берём или снимаем?». Снимаем → `retro_dropped` с причиной.
5. `phase: "scope"`, `status: "черновик"`, `retro.file` или `retro_skipped`.

Собери, проверь, покажи:

```bash
python3 scripts/okr-plan.py render <scope.json> <scope.html>
python3 scripts/okr-plan.py lint <scope.json>
```

### Этап 3: Итерации и выравнивание

PO правит словами или голосом («1.2 — это не наша команда, а партнёр», «добавь
цель про поиск», «PBV у семейной подписки 9, это обещание маркетингу»). Каждый
раз: правка JSON → `render` → `lint` → коротко, что поменялось. HTML руками не
правь.

Когда драфт устоялся — **до** принятия — проведи выравнивание и покажи
замечания одним списком, без правок:

- **Измеримость:** по каждому `result` можно однозначно сказать «сделано»?
- **Реалистичность:** PBV 9 — есть дата и перед кем обещание? PBV ≥ 7 с
  неизвестным объёмом — может, это RESEARCH?
- **Фокус:** 3–5 целей, до 6 инициатив на цель, до 20 всего, не больше двух с PBV 9.
- **Пересечения:** нет ли двух инициатив про одно и то же.
- **Скрытые зависимости:** инициатива явно зависит от команды или системы,
  которой нет в `teams`.
- **Ретро:** всё переходящее либо в плане, либо в `retro_dropped`.

PO решает, что из замечаний принять. Ты не меняешь план сам.

### Этап 4: Принятие

Когда PO говорит «принято»:
1. `python3 scripts/okr-plan.py lint <scope.json> --final`.
2. Ошибки → покажи PO, что мешает принять. Документ остаётся черновиком.
3. Чисто → `status: "принято"`, `updated`, `render`.

## Отчёт

```
Scope <quarter>: .okr/<quarter>/plan/scope-<quarter>.html  [черновик | принято]
Целей N, инициатив N (PBV ≥ 7: N), команд N. Из прошлого квартала: N, снято: N.
[УТОЧНИТЬ]: N. Проверка: OK | ошибок N.

── СТОП ── PO: правьте словами или голосом, я обновлю документ.
Дальше, после «принято»: /okr-stages <quarter>
```
