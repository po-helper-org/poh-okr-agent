# Навык: OKR Scope

## Использование

```
/okr-scope <quarter>
```

Этап 2 из четырёх: `/okr-retro → /okr-scope → (/okr-stages) → /okr-teamplanner`.

## На выходе

```
.okr/<quarter>/plan/scope-<quarter>.json   источник истины
.okr/<quarter>/plan/scope-<quarter>.html   документ, вокруг которого идут правки
```

Формат данных и проверки — `skills/okr-scope/resources/plan_schema.md` (раздел
«Scope»; как запускать скрипт и что значат его ответы — «Работа со скриптом»).
Эталон — `skills/okr-scope/scripts/fixtures/scope-2026Q4.json`: пиши JSON по
его образцу. Скрипт — `<корень установки>/skills/okr-scope/scripts/okr-plan.py`
(корень — куда `install.sh` синкнул навыки, обычно `.claude/`). Ниже он — `okr-plan.py`.

## Принцип

Планирование начинается с разговора с PO, а не с анкеты. Сначала слушаешь
целиком, потом собираешь драфт, потом правите его вместе. Вопросы — только по
тому, без чего драфт не собрать, и по одному. Остальное — `[УТОЧНИТЬ у <кого>]`
в тексте драфта: PO увидит подсветку и поправит сам.

## Инструкция для LLM

### Этап 0: Вводные

1. `.okr/<quarter>/plan/retro-<prev>.json`:
   - принят → бери из него все KR с `next.action: continue` — они переходят в
     квартал; номер KR в новом квартале — `next.kr`, остаток работ — в `comment`
     и незакрытых шагах `plan`;
   - черновик → скажи PO, что ретро не принято, и предложи сначала закончить
     `/okr-retro <quarter>`. PO хочет идти дальше — идём, ссылку на ретро
     всё равно ставим;
   - нет вовсе → спроси, есть ли прошлый квартал. Нет (первое планирование) →
     `retro_skipped` с причиной. Есть → предложи `/okr-retro <quarter>`.
2. `okr-config.md` → `team`, `po_name`, `role_tags`, `teams`.
3. `.okr/index/` (если есть) → команды, системы, стейкхолдеры, глоссарий.
   Нужен только как словарь: правильно назвать команды и системы из рассказа PO.
4. Уже есть `scope-<quarter>.json` → не начинай заново, переходи к Этапу 3.

### Этап 1: Выслушать PO

Отправь ровно это и жди ответа:

> Расскажи мне, что и для каких команд ты хочешь увидеть в <quarter>, в
> открытом виде — как рассказал бы коллеге. Можно голосом. Я из этого соберу
> первичный драфт.
>
> Из прошлого квартала переходит: <список KR ретро с `continue` или
> «ничего»>.

Не перебивай уточнениями. Ответ PO — поток речи: повторы, оговорки, «а, и ещё».
Сохрани его как есть в `po_brief`.

### Этап 2: Первичный драфт

Разбери рассказ:

1. **Команды** → `teams`. Смежные команды, от которых что-то нужно, —
   `external: true`.
2. **Цели** → `objectives`. Группируй инициативы по смыслу, а не по командам.
   Название цели — результат, а не работа: «Продавать подписку без ручных
   операций», а не «Сделать биллинг». `why` — какая боль и что станет лучше.
   Поддержку и регулярные работы — отдельной целью с `activity: true`.
3. **Инициативы** → `initiatives`. Для каждой: `title`, `teams`, `pbv`, `tag`,
   `result`. Для технических переключений — `before`/`after`.
   - `result` — что можно показать в конце квартала, а не «улучшить» и «обеспечить».
   - PBV: 9 — коммитмент с датой перед кем-то, 7–8 — без этого квартал не закрыт,
     5–6 — важно, 3–4 — если хватит сил, 1–2 — гипотеза. Выводи из слов PO
     («маркетинг ждёт к декабрю» → 9); нет сигнала → ставь 5 и помечай
     `[УТОЧНИТЬ PBV]` в `open`.
   - Не знаешь, как делать → `tag: RESEARCH`, результат — согласованный план.
4. **Тип инициативы** → `category`: `Run` — поддержать работающее
   (эксплуатация, баги, техдолг, регулятор), `Change` — развить существующее
   (новые функции, автоматизация), `Disrupt` — создать новое (продукт, канал,
   бизнес-модель). По умолчанию пусто: ставь, только если PO назвал тип или он
   однозначен (поддержка и `ACTIVITY` → `Run`). Сомневаешься — оставь пустым,
   PO решит на странице.
5. **Берём в квартал** → `in_quarter`. В скоуп попадает всё, что PO назвал,
   но в квартал идёт не всё. Явное «делаем» → `true`; «если останется время»,
   «на потом», «не в этот раз» → `false`; неясно → поле не ставь, на странице
   это вопрос PO. Не решай за PO по PBV. Спорную инициативу бизнесу помогает
   решить `/okr-justify <quarter> <KR>` — обоснование «брать или нет».
6. **Переходящее из ретро.** Каждый KR ретро с `continue` — инициатива с
   `from_retro`. PO о нём не упомянул → всё равно добавь и спроси: «<id> из
   прошлого квартала берём или снимаем?». Снимаем → `retro_dropped` с причиной.
7. Шапка: `"kind": "scope"`, `quarter`, `team`, `po`, `updated`, `summary` —
   одна фраза о квартале, `phase: "scope"`, `status: "черновик"`,
   `retro: {"file": "retro-<prev>.json"}` или `retro_skipped` с причиной,
   `po_brief`, `roles` не пиши — по умолчанию подойдут.

Собери, проверь, покажи:

```bash
python3 okr-plan.py lint .okr/<quarter>/plan/scope-<quarter>.json
python3 okr-plan.py render .okr/<quarter>/plan/scope-<quarter>.json .okr/<quarter>/plan/scope-<quarter>.html
```

### Этап 3: Итерации и выравнивание

PO правит словами или голосом («1.2 — это не наша команда, а партнёр», «добавь
цель про поиск», «PBV у семейной подписки 9, это обещание маркетингу»). Каждый
раз: правка JSON → `render` → `lint` → коротко, что поменялось. HTML руками не
правь.

Когда драфт устоялся — **до** принятия — проведи выравнивание и покажи
замечания одним списком, без правок:

- **Измеримость:** по каждому `result` можно однозначно сказать «сделано»?
- **Реалистичность:** PBV 9 — есть дата и перед кем обещание? PBV ≥ 7 с
  неизвестным объёмом — может, это RESEARCH?
- **Фокус:** 3–5 целей, до 6 инициатив на цель, до 20 всего, не больше двух с
  PBV 9 — считая только то, что идёт в квартал. Не влезает → предложи PO, что
  перевести в `in_quarter: false`.
- **Решено по каждой:** у всех инициатив стоит `in_quarter`.
- **Баланс типов:** сколько в квартале Run, Change и Disrupt и сколько без типа.
  Весь квартал в Run — развития нет; ни одного Run — не забыта ли поддержка?
  Решение — за PO.
- **Пересечения:** нет ли двух инициатив про одно и то же.
- **Скрытые зависимости:** инициатива явно зависит от команды или системы,
  которой нет в `teams`.
- **Ретро:** всё переходящее либо в плане, либо в `retro_dropped`.

PO решает, что из замечаний принять. Ты не меняешь план сам.

### Берём в квартал или отменяем

«В этот квартал не берём, но вернёмся» → `"in_quarter": false`: инициатива
остаётся в скоупе кандидатом, строка приглушена, этапов и строк TeamPlanner у
неё нет. «Берём» → `true`. Это не отмена.

### Отмена инициативы

PO снимает инициативу совсем («1.3 снимаем, это больше не нужно») → не удаляй её:
`"status": "Отменено"` и `cancel_reason` с датой. Страница покажет её
зачёркнутой, в счётчики и TeamPlanner она не пойдёт, а решение останется видно.

### Комментарии PO со страницы

PO не правит страницу руками: правым кликом он оставляет комментарий к пункту и
присылает их в чат («Скопировать для агента») или файлом `<файл>.comments.json`.
По каждому комментарию:
1. Найди KR по номеру и поле по разделу (раздел → поле — в `plan_schema.md`,
   «Комментарии PO для агента»).
2. Внеси правку в JSON. Нужен ответ PO, чтобы её сделать, — спроси, не угадывай.
3. После всех правок — `lint` и `render`.
4. Отчитайся списком: номер комментария → что изменил или почему нет.

### Этап 4: Принятие

Когда PO говорит «принято»:
1. `python3 okr-plan.py lint .okr/<quarter>/plan/scope-<quarter>.json --final`.
2. Ошибки → покажи PO, что мешает принять. Документ остаётся черновиком.
3. Чисто → `status: "принято"`, `updated`, `render`.

## Отчёт

```
Scope <quarter>: .okr/<quarter>/plan/scope-<quarter>.html  [черновик | принято]
Целей N, инициатив N, в квартал N (PBV ≥ 7: N), не решено N. Команд N.
Из прошлого квартала: N, снято: N. [УТОЧНИТЬ]: N. Проверка: OK | ошибок N.

── СТОП ── PO: правьте словами или голосом, я обновлю документ.
Дальше, после «принято»: /okr-teamplanner <quarter>
(или сначала /okr-stages <quarter>, если в ПЛАН нужны риски и условия)
```
