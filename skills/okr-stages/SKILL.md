# Навык: Декомпозиция по этапам

## Использование

```
/okr-stages <quarter>
```

Этап 3 из четырёх: `/okr-retro → /okr-scope → /okr-stages → /okr-teamplanner`.

## На выходе

Тот же `.okr/<quarter>/plan/scope-<quarter>.json` / `.html`: у каждой
инициативы появляются заметки `notes` — описание и этапы. Новых документов нет.

Формат `notes` и проверки — `skills/okr-scope/resources/plan_schema.md`.
Скрипт — `<корень установки>/skills/okr-scope/scripts/okr-plan.py` (корень —
куда `install.sh` синкнул навыки, обычно `.claude/`). Ниже он — `okr-plan.py`.

## Принцип

Декомпозиция отвечает на вопрос «что должно произойти, чтобы цель была
достигнута», а не «кто сколько часов потратит». Ресурсы и сроки заполняют
техлиды на этапе 4. Шаги, внешние команды и риски — только из Scope, ретро,
индекса или слов PO. Не знаешь — неопределённость, а не выдуманный шаг.

## Инструкция для LLM

### Этап 0: Вводные

1. `scope-<quarter>.json`:
   - `status: принято`, `phase: scope` → начинаем: ставь `phase: "stages"`,
     `status: "черновик"`;
   - `phase: stages`, черновик → продолжаем с инициатив без `notes`;
   - не принят на этапе 2 → СТОП: «Scope ещё не принят. Сначала /okr-scope <quarter>».
2. Роли этапов — `roles` из Scope (по умолчанию `PO, SA, BE, FE, ADR`).
3. Ретро: у инициатив с `from_retro` возьми `carry_note` — это готовая часть
   описания.

### Этап 1: Декомпозиция инициатив

Иди по инициативам в порядке убывания PBV. `ACTIVITY` пропускай: у поддержки
нет этапов.

Для каждой заполни `notes`:

- `description` — 1–3 предложения: зачем, что входит, чего точно нет.
- `stages` — этапы по порядку. Один этап — один законченный шаг одной роли:
  - `PO` — требования, согласования, приёмка;
  - `SA` — аналитика, контракты, декомпозиция;
  - `ADR` — архитектурное решение;
  - `BE`, `FE` — разработка;
  - шаг внешней команды — `ext: true` рядом с ролью, которая его делает.

  PBV ≥ 7 — не меньше трёх этапов. Для доделки из ретро — только оставшиеся шаги.
- `conditions` — что должно выполниться, чтобы цель была достижима: «тарифы
  утверждены до 20.10», «стенд партнёра доступен с октября».
- `risks` — что может пойти не так и к чему приведёт: «партнёр сдвигает стенд —
  тесты уходят на ноябрь».
- `dependencies` — от кого и чего зависим: команды, системы, решения.
- `uncertainties` — что пока неизвестно и надо устранить. У `RESEARCH` и `POC`
  обязательно.

Работай пачками по 2–3 инициативы. После каждой пачки — `render`, `lint`, и
спроси PO про то, что вывести нельзя: «По 1.2 не понял, кто делает экран
семьи — наш фронт или внешняя команда?». Один вопрос за раз. Нет ответа —
`[УТОЧНИТЬ у <кого>]` в тексте этапа.

```bash
python3 okr-plan.py render <scope.json> <scope.html>
python3 okr-plan.py lint <scope.json>
```

### Этап 2: Сквозная проверка

Когда все инициативы разобраны, покажи PO одним списком:
- инициативы, которые зависят друг от друга (одна ждёт результата другой);
- внешние команды и сколько инициатив от каждой зависит;
- неопределённости, которые блокируют старт.

### Этап 3: Принятие

PO правит словами → правка JSON → `render` → `lint`. HTML руками не правь.

Когда PO говорит «принято»:
1. `python3 okr-plan.py lint <scope.json> --final`.
2. Ошибки → покажи их PO, документ остаётся черновиком.
3. Чисто → `status: "принято"`, `updated`, `render`.

## Отчёт

```
Декомпозиция <quarter>: .okr/<quarter>/plan/scope-<quarter>.html  [черновик | принято]
Разобрано инициатив N из N, этапов N (внешних N). Рисков N, неопределённостей N.
[УТОЧНИТЬ]: N. Проверка: OK | ошибок N.

── СТОП ── PO: проверьте этапы, риски и зависимости.
Дальше, после «принято»: /okr-teamplanner <quarter>
```
