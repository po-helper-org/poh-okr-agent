# Навык: OKR Retro

## Использование

```
/okr-retro <quarter>
```

`<quarter>` — **планируемый** квартал (`2026Q4`). Ретро подводит итоги
предыдущего (`2026Q3`).

Пайплайн планирования — четыре этапа вокруг двух HTML-документов:

```
/okr-retro → /okr-scope → /okr-stages → /okr-teamplanner
```

## На выходе

```
.okr/<quarter>/plan/retro-<prev>.json   источник истины
.okr/<quarter>/plan/retro-<prev>.html   экран итогов для PO
```

Формат данных и проверки — `skills/okr-scope/resources/plan_schema.md`.
Скрипт — `<корень установки>/skills/okr-scope/scripts/okr-plan.py` (корень —
куда `install.sh` синкнул навыки, обычно `.claude/`). Ниже он — `okr-plan.py`.

## Принцип

Ретро — про **факт**, а не про планы. Каждый факт с источником: эпик или задача
трекера, дашборд, релиз, экватор, слова PO с датой. Нет источника —
`[УТОЧНИТЬ у <кого>]`, не придумывай.

## Инструкция для LLM

### Этап 0: Где мы

Проверь `.okr/<quarter>/plan/`:

1. `scope-<quarter>.json` со `status: принято` и `phase: stages` → планирование
   дошло до этапа 4. Скажи это и предложи `/okr-teamplanner <quarter>`.
2. `scope-<quarter>.json` принят, `phase: scope` → предложи `/okr-stages <quarter>`.
3. `scope-<quarter>.json` есть, не принят → предложи продолжить: при
   `phase: stages` — `/okr-stages <quarter>`, иначе `/okr-scope <quarter>`.
4. `retro-<prev>.json` принят → ретро готово, предложи `/okr-scope <quarter>`.
5. Иначе — собирай ретро (Этап 1). Черновик ретро есть → продолжай с него.

Готовое не пересобирай. В отчёте назови, с какого места продолжили.

### Этап 1: Что планировали

Найди план прошлого квартала, первое найденное:
- `.okr/<prev>/plan/scope-<prev>.json` — план из нового пайплайна;
- `.okr/<prev>/OKR-<prev>.md` — план из старого пайплайна;
- `.okr/index/` — если прошлый план лежал где-то в воркспейсе.

Ничего нет → спроси PO: «Какие цели и ключевые результаты были в <prev>?
Можно списком или голосом, как удобно». Из ответа собери `objectives[].krs[]`
с полями `id`, `title`, `plan`.

### Этап 2: Что получилось

Для каждого KR собери факт:
- экватор `.okr/<prev>/equator/экватор-<prev>.md` — статусы на середине квартала
  и открытые вопросы;
- трекер: если в `okr-config.md` задан `tracker_projects` и доступен Atlassian
  MCP — статусы эпиков одним запросом на проект, не на каждый KR;
- остальное — у PO.

Спрашивай PO **одним сообщением** списком KR, где факт неизвестен: «По этим KR
не нашёл результата — расскажи, что получилось». PO может ответить голосом,
сплошным текстом: разбери ответ по KR сам.

Для каждого KR заполни `fact`, `source`, `result`, `progress` (если есть
основание).

### Этап 3: Что переходит

Для каждого KR определи `carry`:
- `Доделка` — KR не закрыт, остаток работ переходит;
- `Продолжение` — KR закрыт или частично, но у него есть следующий шаг;
- `Не переносим` — закрыт без продолжения, отменён или снят.

Для Доделки и Продолжения опиши в `carry_note`, что именно переходит. Сомневаешься
— предложи вариант и спроси PO, не решай молча.

Добавь `summary` (2–3 предложения: главное за квартал), `lessons`,
`open_questions`.

### Этап 4: Сборка и проверка

```bash
python3 okr-plan.py render .okr/<quarter>/plan/retro-<prev>.json .okr/<quarter>/plan/retro-<prev>.html
python3 okr-plan.py lint .okr/<quarter>/plan/retro-<prev>.json
```

Ошибки lint — чини JSON и повторяй. Покажи PO путь к HTML и сводку.

### Этап 5: Итерации и принятие

PO правит словами («1.2 на самом деле доделали», «добавь вывод про партнёра»)
→ правишь JSON → `render` → `lint`. Никогда не правь HTML руками.

Когда PO говорит «принято»:
1. `python3 okr-plan.py lint <retro.json> --final`.
2. Есть ошибки → покажи их PO, ретро остаётся черновиком.
3. Чисто → `status: "принято"`, `updated`, `render`.

## Отчёт

```
Retro <prev>: .okr/<quarter>/plan/retro-<prev>.html  [черновик | принято]
Выполнено N · Частично N · Не выполнено N · Отменено N. Переходит в <quarter>: N.
[УТОЧНИТЬ]: N. Проверка: OK | ошибок N.

── СТОП ── PO: проверьте итоги и то, что переходит.
Дальше, после «принято»: /okr-scope <quarter>
```
