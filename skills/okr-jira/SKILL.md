# Навык: Перенос в JIRA

## Использование

```
/okr-jira <quarter>
```

Идёт последним: `/okr-retro → /okr-scope → (/okr-stages) → /okr-teamplanner → /okr-jira`.

## Принцип

Отдельной структуры для JIRA нет. Декомпозиция эпиков — это TeamPlanner:
KR — эпик, его подзадачи — истории. PO и техлиды правят её на странице
`teamplanner-<quarter>.html`, а `/okr-jira` только переносит принятый
TeamPlanner в JIRA и записывает ключи созданных задач обратно в него.

| В TeamPlanner | В JIRA | Название |
|---|---|---|
| KR, `epic: "enabler"` | Эпик-enabler — инициатива квартала, закрывается БФТ-требованием | `[ТЕГ] название KR` |
| KR, `epic: "epic"` | Эпик — бессрочная работа: `[ACTIVITY]`, поддержка, дежурство | `[ТЕГ] название KR` |
| подзадача (`steps[]`) | История — шаг декомпозиции внутри эпика | `[РОЛЬ] название`, внешняя — `[EXT[BE]] …` |

`epic` не задан — по тегу: `ACTIVITY` → бессрочный эпик, остальное — enabler.

## На выходе

```
.okr/<quarter>/plan/teamplanner-<quarter>.json   + jira_project и jira_key у KR и подзадач
.okr/<quarter>/plan/teamplanner-<quarter>.html   на строке KR виден ключ эпика
.okr/<quarter>/plan/jira-<quarter>.csv           CSV для импорта — только если нет доступа к JIRA
```

Формат — `skills/okr-scope/resources/plan_schema.md`, раздел «TeamPlanner»
(поля `jira_project`, `jira_key`) и «Перенос в JIRA». Скрипт —
`<корень установки>/skills/okr-scope/scripts/okr-plan.py` (корень — куда
`install.sh` синкнул навыки, обычно `.claude/`). Ниже он — `okr-plan.py`.

## Главное правило

**Ни одной задачи в JIRA без явного «да» PO и `ГОТОВО К ПЕРЕНОСУ`.** Молчание,
«посмотрю позже», вопрос или комментарии со страницы — не подтверждение.

## Инструкция для LLM

### Этап 1: Есть ли TeamPlanner

- **Нет `teamplanner-<quarter>.json`** → собери его по навыку
  `skills/okr-teamplanner/SKILL.md` (заготовка `seed` из принятого Scope,
  подзадачи, `lint`, `render`). Отдай страницу PO и остановись — дальше Этап 2.
- **Есть** → `lint` и `render`, чтобы страница была свежей, и сразу Этап 2.
  Заготовку не делай и не перезаписывай: в файле правки техлидов.

### Этап 2: Подтвердить и проверить

```bash
python3 okr-plan.py lint .okr/<quarter>/plan/teamplanner-<quarter>.json --final
```

В чат — коротко, не саму структуру:

```
TeamPlanner для переноса в JIRA: .okr/<quarter>/plan/teamplanner-<quarter>.html
Эпиков N (enabler N, бессрочных N), историй N. Проект: <ключ | не задан>.
Мешает переносу: <ошибки lint --final, до трёх, или «ничего»>.
Переносим в JIRA в таком виде? Правки — на странице («Скачать JSON») или словами.
```

Проект — `okr-config.md → tracker_projects` (первый — по умолчанию); нет или
несколько — спроси PO. **СТОП.** Ждёшь ответа.

Правки (файл со страницы или словами) — как в Этапе 3 `/okr-teamplanner`:
JSON → `lint` → `render` → снова короткий вопрос. Тип эпика PO меняет на
странице: строка KR → «Тип в JIRA».

### Этап 3: После «да»

1. `"status": "принято"`, `"jira_project": "<КЛЮЧ>"`, `updated`.
2. Проверка:
   ```bash
   python3 okr-plan.py jira-ready .okr/<quarter>/plan/teamplanner-<quarter>.json
   ```
   `НЕ ГОТОВО` — покажи PO, что мешает (обычно подзадачи без исполнителя), и
   вернись к Этапу 2.

### Этап 4а: Перенос через Atlassian MCP

Только после `ГОТОВО К ПЕРЕНОСУ`. Идёшь по KR в порядке документа.

1. **Эпик.** Есть `jira_key` — уже создан, пропусти. Иначе поищи в проекте
   эпик с меткой `OKR-<quarter>` и тем же названием: нашёлся — запиши его ключ,
   второй не создавай. Создание:
   - тип — Epic, название — `[ТЕГ] название KR`;
   - описание — `result`, `comment`, текст заметки `details`;
   - метки — `OKR-<quarter>`, `KR-<id>`, `epic-enabler` или `epic-epic`,
     тип (`Change`/`Run`/`Disrupt`), `PBV-<n>`.
2. После **каждой** созданной задачи сразу впиши её ключ (`VIT-123`) в
   `jira_key` и сохрани JSON — прерванный перенос продолжится без дублей.
3. **Истории** — подзадачи KR, так же: пропусти с `jira_key`; тип Story,
   родитель — ключ эпика (Parent или Epic Link — как принято в проекте),
   название — `[РОЛЬ] название`, описание — `result`, `action`, `comment`,
   метки — `OKR-<quarter>`, `KR-<id>`.
4. Ошибка API — остановись, сохрани JSON с уже полученными ключами, покажи PO,
   что создано и на чём встало.
5. В конце — `lint`, `render`: на строках KR видны ключи эпиков.

Никогда: не удаляй и не меняй существующие задачи JIRA, не назначай
исполнителей и спринты, не меняй статусы — только создание. Исполнители и
спринты — по отдельной просьбе PO.

### Этап 4б: Перенос через CSV (нет Atlassian MCP)

```bash
python3 okr-plan.py jira-csv .okr/<quarter>/plan/teamplanner-<quarter>.json .okr/<quarter>/plan/jira-<quarter>.csv
```

Собирается только из принятого TeamPlanner (та же проверка, что `jira-ready`).
Подскажи PO: JIRA → System → External System Import → CSV; `Issue Id` и
`Parent Id` связывают истории с эпиками, `Issue Type` — тип, `Summary` —
название. После импорта ключи можно вписать в `jira_key` по выгрузке из JIRA.

## Отчёт

До подтверждения — четыре строки из Этапа 2 и `── СТОП ──`.

После переноса:
```
JIRA <quarter>: перенесено в <проект> — эпиков N, историй N.
Эпики: <ключи>. Не перенесено: <что и почему или «всё»>.
```
