# Навык: Перенос в JIRA

## Использование

```
/okr-jira <quarter>
```

Идёт после согласованного плана: `/okr-scope` (и `/okr-teamplanner`, если
квартал уже разложен по этапам).

## Главное правило

**Сначала структура — потом JIRA.** Ты всегда показываешь PO верхнеуровневую
структуру переноса — страницу согласования `jira-<quarter>.html` — и
останавливаешься. Ни одной задачи
в JIRA не создаёшь, пока PO явно не подтвердил структуру («да», «переносим»,
«ок, заводи») и `okr-plan.py jira-ready` не ответил `ГОТОВО К ПЕРЕНОСУ`.
Любая правка структуры после подтверждения — снова страница и снова
подтверждение.

## На выходе

```
.okr/<quarter>/plan/jira-<quarter>.json   структура переноса — её пишешь ты
.okr/<quarter>/plan/jira-<quarter>.html   страница согласования — её собирает скрипт
.okr/<quarter>/plan/jira-<quarter>.csv    CSV для импорта JIRA — только если нет доступа к JIRA
```

Формат и проверки — `skills/okr-scope/resources/plan_schema.md`, раздел «JIRA»;
как запускать скрипт — там же, «Работа со скриптом». Эталон —
`skills/okr-scope/scripts/fixtures/jira-2026Q4.json`. Скрипт —
`<корень установки>/skills/okr-scope/scripts/okr-plan.py` (корень — куда
`install.sh` синкнул навыки, обычно `.claude/`). Ниже он — `okr-plan.py`.

## Структура JIRA

| Тип | `type` | Когда |
|---|---|---|
| **Эпик-enabler** | `enabler` | одна инициатива квартала, которая закрывается БФТ-требованием: БФТ определяет объём, эпик закрыт — требование выполнено |
| **Эпик** | `epic` | длительная, бессрочная работа: `[ACTIVITY]`, техподдержка, дежурство — процесс, куда складываются мелкие инициативы |
| **История** | `stories[]` | шаг декомпозиции внутри эпика |

История бывает двух видов:
- **операционная** — шаг большой инициативы одной роли: `[SA]`, `[BE]`, `[FE]`,
  `[QA]`, `[SRE]`, `[PO]`… (`tag`);
- **короткая** — баг, небольшая фича или техдолг, которые помещаются в один
  спринт. Такая инициатива может не получать своего эпика, а лечь историей в
  подходящий бессрочный эпик или в эпик своей темы.

## Инструкция для LLM

### Этап 0: Вводные

1. `scope-<quarter>.json` есть. Лучше принятый; черновик — можно, но всё, где
   «в квартал не решено», будет отмечено и не пройдёт `jira-ready`, пока PO не
   решит.
2. `teamplanner-<quarter>.json` есть → истории берутся из его этапов.
3. Проект JIRA — `okr-config.md → tracker_projects`. Несколько или нет — спроси
   PO, в какой проект переносим.
4. Доступ к JIRA: есть ли инструменты Atlassian MCP (создание задач). Нет —
   перенос будет через CSV-импорт (Этап 4б); скажи это PO заранее.
5. `jira-<quarter>.json` уже есть → продолжаем с ним: в нём могут быть
   подтверждённая структура и ключи уже созданных задач. Заготовку не делай.

### Этап 1: Черновик структуры

```bash
python3 okr-plan.py jira-seed .okr/<quarter>/plan/scope-<quarter>.json .okr/<quarter>/plan/jira-<quarter>.json --teamplanner .okr/<quarter>/plan/teamplanner-<quarter>.json
```

(без TeamPlanner — без `--teamplanner`). Заготовка: эпик на каждую инициативу,
идущую в квартал или с нерешённым `in_quarter`; `[ACTIVITY]` и цели поддержки —
бессрочные эпики, остальное — enabler; истории — из TeamPlanner или этапов
Scope; отменённые и «не в квартал» не переносятся.

Дальше доработай JSON — это твоя часть:
- **Истории из текста.** В образе результата часто перечислены US: «US1: [BUG]
  исправлены ошибки по возвратам» → история `{"code": "US1", "tag": "BUG",
  "title": "исправить ошибки по возвратам"}`. Название — действием: «исправить»,
  «устранить», «описать», а не «исправлены».
- **Нет историй** — возьми этапы из заметок Scope или спроси PO. Не выдумывай.
- **БФТ** у enabler: `bft: "есть"` + `bft_link`, `"нет"` — первой историей
  поставь `[PO] Описать БФТ …`, пусто — не выяснено (покажи PO).
- **Короткие инициативы** (баг, мелкая фича на спринт) — предложи PO перенести
  их историями в подходящий эпик: тогда KR идёт в `from` этого эпика, а свой
  эпик не заводится.
- **Слияние.** Две инициативы — один эпик: оба id в `from`, в `note` — «слит из
  3.10+3.11».
- `title` эпика — как в Scope; `tag` — `BUG`, `RESEARCH`, `POC`, `ACTIVITY`.
  `pbv`, `category` — из Scope, не меняй.
- `labels` — общие метки всех задач (по умолчанию `OKR-<quarter>`).

```bash
python3 okr-plan.py lint .okr/<quarter>/plan/jira-<quarter>.json
```

Ошибки чини в JSON. Предупреждения — покажи PO вместе со структурой.

### Этап 2: Показать структуру и остановиться

```bash
python3 okr-plan.py render .okr/<quarter>/plan/jira-<quarter>.json .okr/<quarter>/plan/jira-<quarter>.html
```

Страница согласования: эпик — строка (тип, название, KR, PBV, сколько историй,
что требует решения), клик — карточка с историями, БФТ и описанием; фильтр
«Требуют решения»; список «Не переносится»; правый клик по эпику или истории —
комментарий для агента.

В чат — **коротко**, три строки, не саму структуру:

```
Структура переноса в JIRA: .okr/<quarter>/plan/jira-<quarter>.html
Эпиков N (enabler N, бессрочных N), историй N. Требуют решения: N — <до трёх самых важных>.
Переносим в таком виде? Правки — словами или комментариями на странице.
```

**СТОП.** Жди ответа. Правки PO (словами или комментариями со страницы) →
правка JSON → `lint` → `render` → снова короткий вопрос. Молчание, «посмотрю
позже» или вопрос — не подтверждение.

`okr-plan.py preview` печатает ту же структуру текстом — для твоей самопроверки
или если PO не может открыть страницу. В чат целиком её не вставляй.

### Комментарии PO со страницы

Правым кликом PO оставляет комментарий к эпику, истории или выделенной зоне и
присылает их в чат («Скопировать для агента») или файлом. По каждому: правка
JSON или вопрос PO; потом `lint`, `render` и отчёт по номерам комментариев.
Комментарии — правки, а не подтверждение.

### Этап 3: Подтверждение

Только после явного «да»: `"status": "подтверждено"`, `updated`, затем

```bash
python3 okr-plan.py jira-ready .okr/<quarter>/plan/jira-<quarter>.json
```

`НЕ ГОТОВО` — покажи PO, что мешает (обычно нерешённое «в квартал» или не
указан проект), и вернись к Этапу 2.

### Этап 4а: Перенос через JIRA (Atlassian MCP)

Только после `ГОТОВО К ПЕРЕНОСУ`.

1. **Эпики, по одному.** Пропускай те, у кого уже есть `key` — они созданы.
   Перед созданием найди в проекте задачу с меткой `OKR-<quarter>` и тем же
   названием: нашлась — запиши её ключ, не создавай вторую.
   - тип — Epic; название — как в preview (`[ТЕГ] название`);
   - описание — `description`, строка БФТ (состояние и ссылка);
   - метки — `labels`, `KR-<id>` для каждого `from`, тип (`Change`/`Run`/`Disrupt`), `PBV-<n>`.
2. После **каждой** созданной задачи сразу впиши её ключ (`ABC-123`) в `key` и
   сохрани JSON — прерванный перенос продолжится без дублей.
3. **Истории** — так же, с родителем = ключ эпика (поле Parent или Epic Link —
   как принято в проекте); название — как в preview (`US1 [SA] — …`).
4. Ошибка API — остановись, сохрани JSON с уже полученными ключами, покажи PO,
   что создано и на чём встало.
5. Все ключи на месте → `"status": "перенесено"`, `lint`, `render` — на
   странице видны ключи.

Никогда: не удаляй и не меняй существующие задачи JIRA, не назначай
исполнителей и спринты, не меняй статусы — только создание по подтверждённой
структуре. Исполнители и спринты — по отдельной просьбе PO.

### Этап 4б: Перенос через CSV (нет доступа к JIRA)

```bash
python3 okr-plan.py jira-csv .okr/<quarter>/plan/jira-<quarter>.json .okr/<quarter>/plan/jira-<quarter>.csv
```

Скрипт соберёт CSV только из подтверждённой структуры. Подскажи PO: JIRA →
System → External System Import → CSV; поля Issue Id и Parent Id связывают
истории с эпиками, Issue Type — тип, Summary — название. После импорта ключи
можно вписать в JSON по выгрузке из JIRA (тогда статус — «перенесено»), иначе
документ остаётся «подтверждено».

## Отчёт

До подтверждения:
```
Структура переноса в JIRA: .okr/<quarter>/plan/jira-<quarter>.html
Эпиков N (enabler N, бессрочных N), историй N. Требуют решения: N — <до трёх>.
── СТОП ── Переносим в таком виде? Правки — словами или комментариями на странице.
```

После переноса:
```
JIRA <quarter>: перенесено в <проект> — эпиков N, историй N.
Эпики: <ключи>. Не перенесено: <что и почему или «всё»>.
```
